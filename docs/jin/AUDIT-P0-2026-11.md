# JIN Trading-Bot – P0 technical audit

Stand: 20. November 2026  
Branch: `jin/10eur-balanced-build`  
Audited baseline: `feat/jin-trading-control` at `f8817cbf6c5afa48c0a1b274dfa59fccfeee034b`

This is a static source/documentation audit. It is not a local test run, an exchange account check, or a live-trading validation.

## Executive result

PR #2 is the strongest foundation for the primary bot. It has a substantial paper-trading service, persistent SQLite state, risk controls, market feeds, dashboard, and automated tests. It is not yet the agreed complete system: the 10 EUR budget is not represented, cross-exchange is not wired into the worker's automatic strategy path, and the 24-hour operating acceptance remains open.

## Findings

### P0 – Must resolve before calling the agreed bot complete

1. **10 EUR is not implemented.**
   - `jin_trading/config.5usdt.json` starts a KuCoin bot with a 5 USDT budget.
   - `jin_trading/worker.py` creates a paper wallet from each bot's `spec['budget']`; its strategy and inventory valuation paths assume USDT.
   - `jin_trading/arbitrage.py`, `jin_trading/execution.py`, and `jin_trading/universe.py` use USDT as the hard-coded start/quote asset.
   - `Store.configure` labels the total budget limit in USDT.
   - Required change: introduce a EUR-denominated portfolio cap, a timestamped EUR/USDT conversion source, explicit quote-currency handling, and a shared aggregate budget check. Do not simply rename 5 USDT to 10 EUR.

2. **Cross-exchange is not integrated as an automatic worker strategy.**
   - `validate_config` explicitly rejects `strategy == 'cross_exchange'`.
   - `Worker.process_books` selects only triangular opportunities for the automatic execution branch.
   - `ExecutionEngine.cross` exists as a separate prefunded paper-only API and explicitly rejects live mode.
   - Required change: integrate a separately configured cross-exchange supervisor path with pre-funded balances, independent venue books, inventory reservations, PnL check, and recovery. Keep live mode blocked until venue-specific acceptance.

3. **Cross-exchange execution needs an explicit profitability gate.**
   - `ExecutionEngine.cross` calculates estimated buy cost and sell value for reservations but does not compare expected net proceeds against cost and `self.min_profit` before submitting the first paper leg.
   - Required change: compute depth-aware, fee-aware net PnL for both venues and reject non-profitable routes before any simulated or real submission. Add regression tests around threshold, fees, slippage, and partial fills.

4. **Fee denomination is not explicit in the book model.**
   - `Book` stores a fee percentage but no fee currency.
   - The quote-to-base branch in `Book.convert` reduces the received base amount by the fee percentage.
   - The current `PaperBroker.submit` records its fee in the quote currency.
   - These are different fee-denomination assumptions. The current conversion can be conservative in some cases, but its reported asset flow is not a faithful model of quote-denominated fees.
   - Required change: model fee amount and fee currency per market/order (base, quote, or third token); keep scanner, paper fills, and live reconciliation consistent.

5. **The 10 EUR cap must be portfolio-wide, not per bot.**
   - The configuration contains a budget per bot and the paper wallet is initialized per bot.
   - The portfolio has a shared deployment ceiling, but the new EUR cap must explicitly bound the sum of all bot allocations and reservations after FX conversion.
   - Required change: enforce the aggregate EUR value of wallets, open reservations, and pending/unknown exposure against 10 EUR. A missing/stale FX mark must block new exposure.

### P1 – Required before production readiness

6. **24-hour operating acceptance is still open.**
   - The acceptance documentation explicitly distinguishes monitoring from execution acceptance.
   - A completed monitor alone does not prove order correctness, fault recovery, or profitable execution.
   - Required change: run a real 24-hour paper soak on a persistent host, with documented feed outage, restart, kill-switch, stale-data, and reconciliation scenarios.

7. **CI evidence is historical, not current.**
   - PR #2 records successful GitHub Actions checks at its October 12, 2026 commit.
   - The current repository view shows those historical runs; it does not prove tests passed on the new working branch.
   - PR #2 documentation says Actions were disabled after a prior run. Workflow availability must be checked before relying on future pushes.

8. **Phone-only operation requires a persistent host.**
   - The mobile dashboard and Docker files exist.
   - The roadmap says a permanent bot host, durable deployment, HTTPS/VPN, backup/restore and phone acceptance are still open.
   - The Android phone is a control surface, not a reliable 24/7 execution host.

## What is already present

- SQLite journal, durable order intent and reservations.
- Paper brokers and sequential IOC simulation.
- Triangle preflight and rejection on stale books / incomplete fills.
- Portfolio loss latch and deployment ceiling.
- Market universe discovery and bounded subscription planning.
- Mobile HTTP dashboard and export endpoints.
- Unit tests and GitHub Actions workflow definitions.

These are useful foundations, not proof of production readiness.

## Status labels

- Implemented: code exists and relevant automated checks are visible.
- Partial: code exists but integration or external acceptance remains open.
- Open: not implemented or not demonstrated.
- Failed: a reproducible test or inspection demonstrates incorrect behavior.

No profitability claim is made by this audit.
